## 3. Теоретические основы

### 3.1. Реляционные соединения (JOIN)
- **INNER JOIN:** Декартово произведение, отфильтрованное по предикату `ON`. Возвращает только те пары строк, для которых условие соединения истинно (`TRUE`). Строки без соответствий отбрасываются.
- **LEFT JOIN (LEFT OUTER JOIN):** Сохраняет все строки левой таблицы. Если в правой таблице соответствие не найдено, поля правой таблицы заполняются значениями `NULL`.
- **Антисоединение (Anti-Join):** Идиома вида `FROM A LEFT JOIN B ON ... WHERE B.id IS NULL`, используемая для эффективного нахождения элементов множества $A \setminus B$ (записи, не имеющие связей в таблице $B$).

### 3.2. Агрегация и фильтрация (GROUP BY и HAVING)
Секция `GROUP BY` делит строки на эквивалентные классы (группы) по значениям указанных столбцов. Каждая группа сворачивается в одну итоговую строку. В списке `SELECT` допустимы только столбцы из `GROUP BY` и агрегатные функции (`COUNT`, `SUM`, `AVG`, `MIN`, `MAX`).  
Различие `WHERE` и `HAVING`:
- `WHERE` фильтрует **исходные кортежи** до их объединения в группы;
- `HAVING` фильтрует **уже агрегированные группы** после их формирования.

### 3.3. Общие табличные выражения (CTE) и рекурсия
Конструкция `WITH` задает временные поименованные наборы строк, существующие в рамках исполнения одного оператора.  
Рекурсивный CTE (`WITH RECURSIVE`) состоит из двух частей, объединённых `UNION ALL`:
1. *Anchor Member (анкерная часть):* базовый запрос, возвращающий корень дерева (начальные строки);
2. *Recursive Member (рекурсивная часть):* запрос, соединяющий исходную таблицу с результатами предыдущей итерации CTE до тех пор, пока очередная итерация не вернет пустое множество.

### 4.4. Задание 4: Применение HAVING для фильтрации групп
**Назначение:** Определение крупных продавцов, чья выручка по завершённым и отправленным заказам превысила 2 000 000 руб.

**Текст SQL-запроса:**
```sql
SELECT 
    s.id                                       AS seller_id,
    s.shop_name                                AS store_title,
    COUNT(DISTINCT o.id)                       AS completed_orders_count,
    SUM(oi.quantity)                           AS total_units_sold,
    ROUND(SUM(oi.quantity * oi.unit_price), 2) AS total_revenue_rub
FROM sellers s
INNER JOIN products p     ON p.seller_id = s.id
INNER JOIN order_items oi ON oi.product_id = p.id
INNER JOIN orders o       ON o.id = oi.order_id
WHERE o.status IN ('delivered', 'shipped')
GROUP BY s.id, s.shop_name
HAVING SUM(oi.quantity * oi.unit_price) > 2000000.00
ORDER BY total_revenue_rub DESC;
```

### 4.6. Задание 6: Общие табличные выражения (CTE)

#### 6.1. Аналитический многошаговый CTE
```sql
WITH seller_sales AS (
    SELECT 
        p.seller_id,
        COUNT(DISTINCT oi.order_id) AS orders_count,
        SUM(oi.quantity * oi.unit_price) AS seller_revenue
    FROM products p
    INNER JOIN order_items oi ON oi.product_id = p.id
    GROUP BY p.seller_id
),
platform_totals AS (
    SELECT SUM(seller_revenue) AS total_platform_revenue FROM seller_sales
)
SELECT 
    s.shop_name AS "Магазин",
    ss.orders_count AS "Заказы",
    ROUND(ss.seller_revenue, 2) AS "Выручка (руб.)",
    ROUND((ss.seller_revenue / pt.total_platform_revenue) * 100, 2) AS "Доля рынка (%)"
FROM seller_sales ss
INNER JOIN sellers s ON s.id = ss.seller_id
CROSS JOIN platform_totals pt
ORDER BY ss.seller_revenue DESC LIMIT 5;
```

#### 6.2. Рекурсивный CTE (WITH RECURSIVE) для обхода дерева категорий
```sql
WITH RECURSIVE category_tree AS (
    -- Анкерная ветвь: корневые категории
    SELECT id, parent_id, name, 1 AS level_depth, name::text AS full_hierarchy_path
    FROM categories WHERE parent_id IS NULL
    UNION ALL
    -- Рекурсивная ветвь: дочерние подкатегории
    SELECT c.id, c.parent_id, c.name, ct.level_depth + 1, ct.full_hierarchy_path || ' -> ' || c.name
    FROM categories c
    INNER JOIN category_tree ct ON ct.id = c.parent_id
)
SELECT id, level_depth AS "Уровень", full_hierarchy_path AS "Полный путь категории"
FROM category_tree
ORDER BY full_hierarchy_path ASC LIMIT 8;
```

## 5. Ответы на контрольные вопросы

### 1. Что такое соединение таблиц и по какому условию оно обычно выполняется?
Соединение (`JOIN`) — это операция реляционной алгебры, объединяющая кортежи двух и более отношений на основе логического предиката связывания. В нормализованных базах данных соединение чаще всего выполняется по условию эквивалентности (Equi-Join) первичного ключа родительской таблицы и внешнего ключа дочерней таблицы (`ON parent.id = child.parent_id`).

### 2. Чем INNER JOIN отличается от LEFT JOIN? Приведите пример, где нужен именно LEFT JOIN.
`INNER JOIN` возвращает только те строки, для которых найдено соответствие в обеих таблицах. Если строка одной из таблиц не удовлетворяет условию связи, она исключается из результата.  
`LEFT JOIN` гарантированно сохраняет все строки левой таблицы. Если в правой таблице соответствие отсутствует, её столбцы заполняются `NULL`.  
*Пример:* вывод полного списка пользователей или товаров с количеством их отзывов (`products LEFT JOIN reviews`). Если использовать `INNER JOIN`, товары без отзывов вообще исчезнут из выборки, что исказит аналитику каталога.

### 3. Какие агрегатные функции вы знаете? В чём различие между COUNT(*) и COUNT(столбец)?
Основные агрегатные функции: `COUNT` (число строк), `SUM` (сумма), `AVG` (среднее арифметическое), `MIN` (минимум), `MAX` (максимум).  
Различие:
- `COUNT(*)` подсчитывает **абсолютно все строки** в группе, включая те, которые состоят исключительно из `NULL`;
- `COUNT(column)` подсчитывает только строки, в которых значение `column` **не равно NULL**.

### 4. Для чего предназначена секция GROUP BY и что допустимо в списке выборки при группировке?
Секция `GROUP BY` сжимает исходный массив строк в группы с одинаковыми значениями ключей группировки. В секции `SELECT` допустимо указывать **только**:
1. Столбцы, явно перечисленные в секции `GROUP BY` (а также функционально зависимые от первичного ключа столбцы в PostgreSQL);
2. Агрегатные функции над любыми другими столбцами (`SUM`, `AVG`, `COUNT` и т.д.);
3. Литералы и константные выражения.

### 5. В чём различие между WHERE и HAVING и в каком порядке они выполняются?
- `WHERE` выполняется **до группировки** (шаг 2 логического порядка) и фильтрует индивидуальные исходные строки. В `WHERE` запрещено использовать агрегатные функции.
- `HAVING` выполняется **после группировки** (шаг 4) и фильтрует уже сформированные агрегированные группы строк на основе условий над агрегатами (`HAVING SUM(amount) > 1000`).

### 6. Что такое подзапрос? Чем коррелированный подзапрос отличается от некоррелированного?
Подзапрос — это вложенный оператор `SELECT`, заключенный в круглые скобки.
- **Некоррелированный подзапрос:** не зависит от внешнего запроса. Он вычисляется планировщиком один раз, после чего его результат многократно используется внешним запросом.
- **Коррелированный подзапрос:** содержит ссылки на поля внешнего запроса (`p.seller_id = s.id`). Логически он должен вычисляться заново для каждой строки внешнего запроса, поэтому потенциально более ресурсоёмок.

### 7. Как работает предикат EXISTS и когда его удобно применять?
Предикат `EXISTS (subquery)` возвращает `TRUE`, если подзапрос возвращает хотя бы одну строку, и `FALSE`, если подзапрос пуст. Оптимизатор PostgreSQL прекращает выполнение подзапроса сразу после нахождения первой подходящей строки (`Short-Circuit Evaluation`). `EXISTS` идеально подходит для проверки факта наличия связанных записей (например, «есть ли у продавца товары на складе») и, в отличие от `IN`, не подвержен проблемам с трехзначной логикой при наличии `NULL`.

### 8. Что такое общее табличное выражение (CTE) и для чего нужен рекурсивный CTE?
`CTE (Common Table Expression)` — временная именованная выборка (`WITH name AS (...)`), повышающая читаемость и модульность сложных запросов.  
`Рекурсивный CTE (WITH RECURSIVE)` предназначен для обхода графовых и иерархических структур данных произвольной глубины (деревья категорий, организационные структуры, маршруты) за счет циклического вызова дочерней ветви до исчерпания связей.

### 9. Что такое представление (VIEW)? Хранит ли обычное представление данные?
Обычное представление (`VIEW`) — это виртуальная таблица, представляющая собой сохраненный SQL-запрос. Обычное представление **не хранит данные на диске**. При каждом обращении к `VIEW` СУБД производит подстановку его текста в основной запрос на этапе синтаксического анализа (Query Rewrite).

### 10. Чем материализованное представление отличается от обычного?
`MATERIALIZED VIEW` физически сохраняет результат выполнения запроса на диске в виде реальной таблицы.  
- **Преимущество:** мгновенная скорость чтения тяжёлых агрегатов без повторных вычислений. Допускает построение собственных индексов.
- **Недостаток:** данные не обновляются автоматически при изменении базовых таблиц; требуется периодический вызов команды `REFRESH MATERIALIZED VIEW`.
