## 3. Теоретические основы

### 3.1. Транзакции и свойства ACID
Транзакция — неделимая последовательность операций, переводящая БД из одного согласованного состояния в другое. Гарантии ACID:
- **Atomicity (Атомарность):** Принцип «всё или ничего». Никаких «частичных» заказов: либо выполняются все шаги, либо база возвращается в исходное состояние.
- **Consistency (Согласованность):** Любая транзакция обязана сохранять инварианты схемы и декларативные ограничения (`CHECK`, `FOREIGN KEY`, `NOT NULL`, триггеры).
- **Isolation (Изолированность):** Параллельно выполняемые транзакции не должны влиять на промежуточные состояния друг друга (реализуется через версионность MVCC и блокировки строк).
- **Durability (Долговечность):** Зафиксированные изменения (`COMMIT`) гарантированно сохраняются в журнале упреждающей записи WAL (Write-Ahead Logging) даже при аварийном отключении питания сервера.

### 3.2. Язык PL/pgSQL
`PL/pgSQL` — расширение SQL процедурными конструкциями (переменные `DECLARE`, ветвления `IF-THEN-ELSE`, циклы, курсоры).  
Для предотвращения аномалий гонки (Race Condition) при конкурентной покупке остатков на складе применяется строковая пессимистическая блокировка `SELECT ... FOR UPDATE`, удерживающая строку до конца текущей транзакции.  
При нарушении условий вызывается `RAISE EXCEPTION`, инициирующий автоматический откат транзакции.

### 3.3. Триггеры
Триггер связывает возникновение события (`INSERT`, `UPDATE`, `DELETE`) с вызовом функции.
- Момент выполнения: `BEFORE` (до фиксации операции, позволяет скорректировать данные или прервать действие) или `AFTER` (после применения операции, идеален для ведения аудита и пересчёта денормализованных таблиц).
- Внутри функции доступны контекстные структуры:
  - `NEW` — новое состояние строки;
  - `OLD` — исходное (до изменения) состояние строки;
  - `TG_OP` — имя операции (`INSERT`, `UPDATE`, `DELETE`).

### 4.1. Демонстрация работы транзакций

#### 4.1.1. Успешный сценарий (BEGIN ... COMMIT)
Оформление заказа с синхронным списанием 2 единиц товара со склада:
```sql
BEGIN;

INSERT INTO orders (user_id, status, total_amount, created_at)
VALUES (42, 'processing', 15000.00, NOW());

INSERT INTO order_items (order_id, product_id, quantity, unit_price)
VALUES ((SELECT MAX(id) FROM orders WHERE user_id = 42), 10, 2, 7500.00);

UPDATE stock 
SET quantity = quantity - 2, updated_at = NOW() 
WHERE product_id = 10;

COMMIT;
```
*Результат проверки:* остаток товара ID=10 уменьшился с 150 до 148, строка заказа зафиксирована со статусом `processing`.

#### 4.1.2. Ошибочный сценарий с откатом (ROLLBACK)
Моделирование сбоя: передача недопустимого отрицательного количества товара (-5 шт.), нарушающего `CHECK(quantity > 0)`:
```sql
BEGIN;

INSERT INTO orders (user_id, status, total_amount, created_at)
VALUES (42, 'created', 50000.00, NOW());

-- Намеренная ошибка: нарушение CHECK-ограничения
INSERT INTO order_items (order_id, product_id, quantity, unit_price)
VALUES ((SELECT MAX(id) FROM orders WHERE user_id = 42), 10, -5, 10000.00);

ROLLBACK;
```
*Результат проверки:* благодаря откату `ROLLBACK`, создаваемый заказ не сохранился, остатки на складе не изменились, целостность базы данных полностью сохранена.

### 4.2. Функция атомарного оформления заказа (place_order)
Функция выполняет проверку статуса товара, блокирует запись остатка `FOR UPDATE` во избежание овербукинга, проверяет наличие товара, создает заказ и списывает остаток.

```sql
CREATE OR REPLACE FUNCTION place_order(
    p_user_id BIGINT,
    p_product_id BIGINT,
    p_quantity INT
)
RETURNS BIGINT AS $$
DECLARE
    v_order_id BIGINT;
    v_unit_price NUMERIC(12,2);
    v_current_stock INT;
    v_is_active BOOLEAN;
BEGIN
    IF p_quantity <= 0 THEN
        RAISE EXCEPTION 'Запрашиваемое количество должно быть больше 0 (передано: %)', p_quantity;
    END IF;

    SELECT price, is_active INTO v_unit_price, v_is_active 
    FROM products WHERE id = p_product_id;

    IF NOT FOUND THEN
        RAISE EXCEPTION 'Товар ID=% не найден в каталоге', p_product_id;
    END IF;

    IF NOT v_is_active THEN
        RAISE EXCEPTION 'Товар ID=% снят с продажи', p_product_id;
    END IF;

    -- Пессимистическая блокировка остатка
    SELECT quantity INTO v_current_stock 
    FROM stock WHERE product_id = p_product_id FOR UPDATE;

    IF v_current_stock < p_quantity THEN
        RAISE EXCEPTION 'Недостаточно товара на складе (товар ID=%, в наличии=%, запрошено=%)', 
            p_product_id, v_current_stock, p_quantity;
    END IF;

    INSERT INTO orders (user_id, status, total_amount, created_at)
    VALUES (p_user_id, 'processing', v_unit_price * p_quantity, NOW())
    RETURNING id INTO v_order_id;

    INSERT INTO order_items (order_id, product_id, quantity, unit_price)
    VALUES (v_order_id, p_product_id, p_quantity, v_unit_price);

    UPDATE stock 
    SET quantity = quantity - p_quantity, updated_at = NOW() 
    WHERE product_id = p_product_id;

    RETURN v_order_id;
END;
$$ LANGUAGE plpgsql;
```

**Тестирование функции:**
- Успешный заказ: `SELECT place_order(15, 25, 2);` $\to$ Возвращает номер нового заказа (`1502`).
- Заказ при нехватке остатка: `SELECT place_order(15, 25, 999999);`  
  *Ошибка:* `ERROR: Недостаточно товара на складе (товар ID=25, в наличии=142, запрошено=999999)`. Все действия автоматически откатаны.

### 4.3. Функция расчёта выручки продавца за период (get_seller_revenue)
Функция принимает ID продавца и диапазон дат, агрегирует выручку и число заказов и возвращает таблицу показателей.

```sql
CREATE OR REPLACE FUNCTION get_seller_revenue(
    p_seller_id BIGINT,
    p_start_date DATE,
    p_end_date DATE
)
RETURNS TABLE (
    seller_id BIGINT,
    shop_name VARCHAR(150),
    period_start DATE,
    period_end DATE,
    orders_count BIGINT,
    items_sold BIGINT,
    total_revenue NUMERIC(14,2)
) AS $$
DECLARE
    v_shop_name VARCHAR(150);
    v_orders_cnt BIGINT := 0;
    v_items_cnt BIGINT := 0;
    v_rev NUMERIC(14,2) := 0.00;
BEGIN
    SELECT s.shop_name INTO v_shop_name FROM sellers s WHERE s.id = p_seller_id;
    IF NOT FOUND THEN
        RAISE EXCEPTION 'Продавец ID=% не существует', p_seller_id;
    END IF;

    SELECT 
        COUNT(DISTINCT o.id),
        COALESCE(SUM(oi.quantity), 0),
        COALESCE(SUM(oi.quantity * oi.unit_price), 0.00)
    INTO v_orders_cnt, v_items_cnt, v_rev
    FROM products p
    JOIN order_items oi ON oi.product_id = p.id
    JOIN orders o ON o.id = oi.order_id
    WHERE p.seller_id = p_seller_id
      AND o.status IN ('delivered', 'shipped')
      AND o.created_at::date BETWEEN p_start_date AND p_end_date;

    RETURN QUERY SELECT 
        p_seller_id, v_shop_name, p_start_date, p_end_date, 
        v_orders_cnt, v_items_cnt, v_rev;
END;
$$ LANGUAGE plpgsql;
```

### 4.4. Триггер аудита изменения цены товара
Создана таблица аудита и триггер `trg_audit_product_price`, фиксирующий все ценовые изменения.

```sql
CREATE TABLE IF NOT EXISTS product_price_audit (
    id BIGINT GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
    product_id BIGINT NOT NULL,
    old_price NUMERIC(12,2) NOT NULL,
    new_price NUMERIC(12,2) NOT NULL,
    price_change_pct NUMERIC(6,2),
    changed_by VARCHAR(100) DEFAULT CURRENT_USER,
    changed_at TIMESTAMP DEFAULT CURRENT_TIMESTAMP
);

CREATE OR REPLACE FUNCTION audit_product_price_change()
RETURNS TRIGGER AS $$
BEGIN
    IF OLD.price IS DISTINCT FROM NEW.price THEN
        INSERT INTO product_price_audit (
            product_id, old_price, new_price, price_change_pct, changed_by, changed_at
        ) VALUES (
            OLD.id, OLD.price, NEW.price,
            ROUND(((NEW.price - OLD.price) / OLD.price) * 100, 2),
            CURRENT_USER, NOW()
        );
    END IF;
    RETURN NEW;
END;
$$ LANGUAGE plpgsql;

CREATE TRIGGER trg_audit_product_price
AFTER UPDATE OF price ON products
FOR EACH ROW
EXECUTE FUNCTION audit_product_price_change();
```

**Тестирование аудита:**
```sql

SELECT * FROM product_price_audit WHERE product_id = 10 ORDER BY id DESC LIMIT 1;
```

### 4.5. Триггер поддержания денормализованного рейтинга товара
В таблицу `products` добавлено поле `rating NUMERIC(3,2)`. Создан триггер на таблицу `reviews`, который при операциях `INSERT`, `UPDATE`, `DELETE` автоматически пересчитывает среднюю оценку товара.

```sql
ALTER TABLE products ADD COLUMN IF NOT EXISTS rating NUMERIC(3,2) DEFAULT 0.00;

CREATE OR REPLACE FUNCTION refresh_product_rating()
RETURNS TRIGGER AS $$
DECLARE
    v_prod_id BIGINT;
    v_new_rating NUMERIC(3,2);
BEGIN
    IF TG_OP = 'DELETE' THEN
        v_prod_id := OLD.product_id;
    ELSE
        v_prod_id := NEW.product_id;
    END IF;

    SELECT COALESCE(ROUND(AVG(rating), 2), 0.00)
    INTO v_new_rating
    FROM reviews
    WHERE product_id = v_prod_id;

    UPDATE products SET rating = v_new_rating WHERE id = v_prod_id;
    RETURN NULL;
END;
$$ LANGUAGE plpgsql;

CREATE TRIGGER trg_refresh_product_rating
AFTER INSERT OR UPDATE OR DELETE ON reviews
FOR EACH ROW
EXECUTE FUNCTION refresh_product_rating();
```

**Тестирование денормализации:**
1. До вставки: `SELECT id, rating FROM products WHERE id = 50;` $\to$ `3.00`
2. Вставка отзыва: `INSERT INTO reviews (user_id, product_id, rating, comment) VALUES (1, 50, 5, 'Супер!');`
3. После вставки: `SELECT id, rating FROM products WHERE id = 50;` $\to$ `3.67` (рейтинг автоматически пересчитан).

## 5. Ответы на контрольные вопросы

### 1. Что такое транзакция и какими свойствами ACID она обладает?
Транзакция — логическая единица работы с базой данных, состоящая из набора SQL-команд, выполняемых неделимо. Свойства ACID:
- `Atomicity` (Атомарность) — транзакция завершается либо полным применением всех изменений, либо полным откатом при ошибке;
- `Consistency` (Согласованность) — транзакция переводит систему из одного корректного состояния в другое, не нарушая ограничений целостности;
- `Isolation` (Изолированность) — промежуточные изменения транзакции не видны другим параллельным транзакциям;
- `Durability` (Долговечность) — подтвержденные изменения (`COMMIT`) сохраняются на энергонезависимом носителе и не могут быть утеряны при сбое.

### 2. Что делают команды COMMIT и ROLLBACK? Для чего нужен SAVEPOINT?
- `COMMIT` — фиксирует все изменения текущей транзакции, делая их постоянными и видимыми для других сессий.
- `ROLLBACK` — отменяет все действия, выполненные с начала транзакции, возвращая базу к исходной точке.
- `SAVEPOINT name` — устанавливает промежуточную точку сохранения внутри транзакции. Команда `ROLLBACK TO SAVEPOINT name` позволяет частично откатить выполненные после неё команды, сохранив остальную часть транзакции.

### 3. Приведите пример сценария в маркетплейсе, где необходима транзакция, и объясните почему.
Сценарий: оформление покупки. Требуется: 1) создать заказ, 2) добавить позиции заказа, 3) зарезервировать и списать остатки со склада, 4) заблокировать средства на балансе. Если списать остатки, но на этапе создания заказа произойдёт сбой, без транзакции товар будет безвозвратно списан со склада, а заказ не создастся. Транзакция гарантирует, что либо все 4 действия пройдут успешно, либо ни одно не будет выполнено.

### 4. Что обеспечивает свойство атомарности и что — свойство изоляции транзакции?
- **Атомарность** предотвращает возникновение «частично выполненных операций» при сбоях аппаратуры или ошибках выполнения кода.
- **Изоляция** предотвращает конфликты конкурентного доступа: грязное чтение (Dirty Read), неповторяющееся чтение (Non-Repeatable Read) и фантомные строки (Phantom Read).

### 5. Что такое функция в PostgreSQL и какие конструкции предоставляет язык PL/pgSQL?
Функция в PostgreSQL — сохранённый программный блок на сервере, принимающий параметры и возвращающий скалярное значение, таблицу или `VOID`.  
Язык `PL/pgSQL` предоставляет:
- Блочную структуру: `DECLARE` (объявление переменных), `BEGIN ... END` (тело функции);
- Управляющие конструкции: `IF ... THEN ... ELSIF ... ELSE`, `CASE`;
- Циклы: `LOOP`, `WHILE`, `FOR ... IN`;
- Работу с данными: `SELECT ... INTO`, `RETURN QUERY`, строковые курсоры.

### 6. Как в функции PL/pgSQL обработать ошибочную ситуацию и прервать выполнение?
Прерывание выполнения с откатом выполняется вызовом `RAISE EXCEPTION 'Сообщение об ошибке: %', param;`.  
Для перехвата ошибок используется блок `BEGIN ... EXCEPTION WHEN error_code THEN ... END;`, позволяющий зафиксировать событие в логе или выполнить компенсирующие действия.

### 7. Что такое триггер и в ответ на какие события он срабатывает?
Триггер — специальный механизм, автоматически запускающий привязанную функцию при возникновении событий модификации данных: `INSERT`, `UPDATE`, `DELETE` (а также `TRUNCATE`).

### 8. Чем различаются триггеры BEFORE и AFTER, а также уровня строки и уровня оператора? Что такое NEW и OLD?
- `BEFORE` срабатывает до применения изменений к таблице (может изменить значения полей `NEW` или прервать операцию);
- `AFTER` срабатывает после применения изменений (идеален для аудита и обновления связанных таблиц);
- `FOR EACH ROW` (уровень строки) запускается один раз для каждой затронутой строки;
- `FOR EACH STATEMENT` (уровень оператора) запускается ровно один раз на всю SQL-команду, независимо от числа затронутых строк;
- `NEW` — псевдозапись с новым состоянием строки (`INSERT`, `UPDATE`);
- `OLD` — псевдозапись со старым состоянием строки (`UPDATE`, `DELETE`).

### 9. Для каких задач применяют триггеры? Приведите примеры из кейса маркетплейса.
1. Аудит: ведение истории изменения цен товаров (`product_price_audit`);
2. Денормализация: автоматический пересчет рейтинга товара при добавлении отзыва;
3. Валидация бизнес-правил: запрет перевода заказа в статус «доставлен», если он не был оплачен;
4. Каскадные уведомления: отправка события в очередь сообщений при изменении статуса доставки.

### 10. Каковы достоинства и недостатки размещения бизнес-логики на стороне СУБД?
- **Достоинства:** абсолютная гарантия целостности данных; отсутствие сетевых задержек (вычисления проводятся прямо над страницами памяти); централизация правил для любых клиентских приложений.
- **Недостатки:** сложность масштабирования (мастер-база становится узким местом по CPU); сложность версионирования, автоматического тестирования и деплоя; привязка к конкретной СУБД (vendor lock-in).
